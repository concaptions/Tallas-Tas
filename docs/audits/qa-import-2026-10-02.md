## THE IMPORT SLICING HAZARD — do not design around it

`importAirtableExport` pass 2 **clears each junction for the records it imported and re-links from the
export**. The clear is `airtable-import.ts:1498–1501`:

```
const clear = async (junction: PgTable, column: AnyPgColumn, ids: IdMap) => {
  const values = [...ids.values()];
  if (values.length > 0) await db.delete(junction).where(inArray(column, values));
};
```

followed by 21 `await clear(...)` calls at `airtable-import.ts:1502–1522`. The deletion key is the
**owning** side's id map. So for any junction whose owner is in the export, every existing row is
deleted, and only what the export can resolve is written back. If the export carries the owner but not
the link target, the target's id map is empty, `resolveRefs` returns nothing, and **the links are
deleted and not restored**.

This is not hypothetical. On 2026-10-02 a slice of Concepts without Angles took `concept_angles` from
115 rows to 4 in production. `concept_angles` now reads 111 (healed by a later full-chain run), but
**`creator_products` is sitting at 0 against 63 expected pairs, with all 70 creators and all 6 products
present** — the same failure mode, not yet healed.

**Therefore: any re-import must be dependency-closed.** A slice must carry every table that the slice's
junctions resolve against, or it will delete links it cannot rebuild. The dependency closure for each
junction, read off the `clear` calls and the pass-2 loops:

| Junction cleared | Owner table that triggers the clear | Must ALSO be in the export |
|---|---|---|
| `concept_angles`, `concept_themes`, `concept_collections` | Concepts | Angles, Themes, Collections |
| `angle_personas`, `angle_products` | Angles **and** Concepts (inference) | Personas, Products, Angles, Concepts |
| `creator_concepts`, `creator_products` | Creators | Concepts, Products |
| `creative_module_angles`, `creative_module_designs` | (Internal) Creative Modules | Angles, Creative Design |
| `campaign_concepts` | Campaigns & Offers | Concepts |
| `copywriting_copy_types`, `copywriting_campaigns` | Meta Copywriting | Copy Type, Campaigns & Offers |
| the four `youtube_copy_*` | Youtube Copywriting | Collections, Products, Campaigns & Offers, Copy Type |
| the three `email_campaign_*` | Email Campaigns Management | Campaigns & Offers, Products, Collections |
| `email_flow_campaigns` | Email Flows Management | Campaigns & Offers |

Note the asymmetry that makes this easy to get wrong: `clear` is a no-op when the owner's id map is
empty, so a run that omits the owner is harmless, while a run that includes the owner and omits a
target is destructive. A Creators-only slice is destructive; a Products-only slice is not.

## Em-dash causes, grouped by cause

### Cause A — MAPPED-BUT-NEVER-IMPORTED (the mapping is right; the rows were never written)

**A1. `creative_sheet_items` — 0 rows against 377 live Airtable records.** The whole Creative Sheet
table is absent from production. The engine's mapper is complete and correct
(`airtable-import.ts:1369–1398`): `briefId`, `internalStatus`, `status`, `qaChecklistDoc`,
`qaVideoEditor`, `qaDesigner`, `qaStrategist`, `clientComments`, `used`, `deniedRevisionsNeeded`,
`winning`, `spellCheckRequested`, `spellingFeedback`. Nothing is unmapped. The table has simply never
been imported for Gratsi. Every field on every Creative Sheet screen shows an em dash — or, more
precisely, the screen is empty.

What a re-import would fill, from the live populated counts: `brief_id` 377, `status` 377,
`qa_checklist_doc` 377, `spelling_feedback` 67, `spell_check_requested` 5 true. The other eight
columns would stay empty **because the Airtable fields are empty**: `Internal Status` 0, the three QA
checkboxes 0, `Client's Comments` 0, `Used` 0, `Denied/revisions needed` 0, `Winning` 0.

**A2. `creative_modules` — 0 rows against 35 live Airtable records**, and with it
`creative_module_designs` at 0 against 226 expected pairs. The mapper
(`airtable-import.ts:1353–1361`) writes `moduleName` and `foreplayLink`; the pass-2 loop
(`airtable-import.ts:1751–1772`) writes both junctions. Nothing is unmapped. A re-import would fill
`module_name` 35 and `creative_module_designs` 226. `foreplay_link` would stay empty (live `Foreplay
Link` = 0 populated) and `creative_module_angles` would stay at 0 (live `Concepts` = 0 populated).
This is also why the Creative Module column is blank on all 225 briefs that carry one in Airtable.

### Cause B — UNMAPPED (no column exists, so the datum has nowhere to land)

**B1. `Personas.Passion` — 23 of 28 live records populated, no column.** `personas` has no column for
it (verified against `information_schema`), and `import-mappings.ts:240` declares it
`handler: 'skip'` on purpose, citing `docs/decisions/gratsi-unmapped-fields-2026-10-02.md`. It is a
pinned display field with real data in 23 records; a re-import changes nothing. Fixing it needs a
migration, not an import.

**B2. `Concepts.Performance` — 18 of 102 live records populated, no column.** `concepts` has no
`performance` column in production. The engine's concepts mapper (`airtable-import.ts:918–952`) never
reads `f.Performance`. **`import-mappings.ts:511` claims `Performance: { drizzleColumn: 'performance',
handler: 'select' }` — the mapping file is wrong on both counts**: no such column, and the engine does
not read the field. A re-import changes nothing; this needs a migration.

**B3. `Meta Copywriting.Angle` and `Meta Copywriting.Collections`; `(Internal) Creative
Design` (second link) on Meta Copywriting; `Angles.Creators`; `UGC Management.Concepts`;
`Client Assets Organisation.(Internal) Creative Design`.** All are genuinely unmapped, and all are at
**0 populated in the live base**, so none of them is an em-dash cause today. Listed for completeness,
not as a defect to chase.

**B4. `creative_dimensions.creative_design_id` — the column exists and is never written (0 non-null).**
The live `(Internal) Creative Dimensions › (Internal) Creative Design` link is populated on 3 of 22
records. The relation is not lost: the brief side stores the dimension **names** in
`creative_briefs.dimensions` (361 of 390 non-empty, resolved at `airtable-import.ts:972–992`). So the
dimension→brief direction is an unwritten column, while the brief→dimension direction is populated.

### Cause C — MAPPED but the junction never resolves

**C1. `concept_themes` = 0 against 27 theme names on Concepts.** Two independent reasons, both real:

1. **The live Themes table is empty of data.** All 3 Themes records carry no stored field at all —
   `Name` is 0 populated, and the only field present is the `Attachment Summary` AI field in an
   `emptyDependency` error state. The three rows imported into production are therefore all named
   `Untitled` (`themes.name` = `Untitled` for each of the 3 rows carrying a `legacy_airtable_id`).
2. **The name-matcher only considers themes inside the same export.** At
   `airtable-import.ts:1580–1592` the matcher loops `themeMap.entries()` — the rows *this import*
   wrote — and compares `str(themeRec.fields.Name)` to the concept's theme name. Because the three
   imported themes have no `Name`, the comparison can never succeed; and because the 6 seed themes in
   the global library are not in `themeMap`, they are unreachable by the matcher regardless.

The 24 distinct theme names the Concepts rows actually carry — `Casual Interview`, `Aspirational
Lifestyle`, `Listicle`, `Contextual Endorsement`, `Problem Solution`, `Interactive Quiz`, `Yapper
Review`, `Comparison`, `Pattern Interrupt`, `Explainer`, `Product Discovery`, `Taste Test`, `Product
Demo`, `Price Reveal`, `Experience Sharing`, `GRWM`, `Food Pairing`, `POV Style`, `This vs. That`,
`Social Proof`, `Recommendation`, `Group Reaction`, `Problem Solution Skit`, `Day in the Life` —
**match none of the 6 seed theme names** (`Green Screen`, `Holiday Gifting`, `POV: X vs Y`,
`Problem/Solution`, `Spring x Soccer`, `Yapper Style`) exactly. `Problem Solution` vs
`Problem/Solution` and `POV Style` vs `POV: X vs Y` are near-misses, not matches.

**So a re-import would not fix the Theme column.** It needs 24 theme rows created in the global library
with those exact names (themes are global per non-negotiable 3), and then a re-import of Concepts.
Until then every concept row shows an em dash in the Theme column
(`concepts-workspace.tsx:166`).

**C2. `creator_products` = 0 against 63 expected pairs.** The mapping is correct and so is the engine:
`airtable-import.ts:1853` reads `rec.fields.Products ?? rec.fields.Product` against `prodMap`, the
live field is named `Products` exactly, it links `(Internal) Product`, and 27 of 70 creators carry it.
All 6 products and all 70 creators are in production. The junction is nonetheless empty, which is the
signature of the slicing hazard above: a run that carried Creators (so `clear` fired) without Products
(so `prodMap` was empty). `creator_concepts` at 87/87 in the same table shows that run did carry
Concepts. **I could not establish from the database which export that run used**; what is established
is that the mapping is right, the data is present on both sides, and the links are gone. Cause:
MAPPED-BUT-CLEARED. A dependency-closed re-import of Creators + Concepts + Products restores all 63.

### Cause D — WRONG-TARGET read (no wrong data written, but a column stays empty)

**D1. `collections.angle_id` — the engine resolves a Concepts link against the Angles id map.**
`airtable-import.ts:1631` is `const angleId = firstRef(angleMap, rec.fields.Angles ?? rec.fields.Angle);`.
The live `(Internal) Collections › Angles` field **links the Concepts table**, not Angles (confirmed
from the field's `linkedTableId` in the base metadata), and is populated on 3 of 5 records. Concept
record ids are never in `angleMap`, so the lookup always misses and `collections.angle_id` stays NULL
(0 non-null in production). Nothing wrong is written — but the read is aimed at the wrong table.
`import-mappings.ts:457` declares this field `handler: 'skip'`, so **the engine reads a field the
mapping file says it ignores.** The datum itself is not lost: the same relation is stored as
`concept_collections` (207 rows, complete).
